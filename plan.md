# Postzyo Growth and Product Implementation Plan

**Planning baseline** — 19 November 2026, repository commit `456cc8e`, and public HTTP checks of `postzyo.com`.

**Goal** — Help more operators discover Postzyo, publish their first Facebook or Instagram post successfully, return to run their weekly publishing workflow, and convert into profitable paid accounts.

**Architecture** — Keep Django templates and JavaScript, PostgreSQL, Redis, Celery and the existing Meta integration. Make PostgreSQL authoritative for publishing and payment outcomes. Add focused public Django pages on the same domain and improve the existing workspace progressively.

**Scope** — This is the execution roadmap. Target values and prices marked as experiments are proposals. Current functionality and operational context are documented in [Social Media Automation.md](Social%20Media%20Automation.md).

## Product and rollout decisions

- Start with India-based solo social media managers and small-agency operators responsible for several Facebook Pages or Instagram professional accounts. This is an initial market hypothesis based on INR billing and the existing bulk scheduling flow. In week 1, interview 5–8 consenting operators about account setup, weekly publishing volume, failures, time spent reporting and willingness to pay. Validate whether agency operators will buy before investing in team roles.
- Lead with one clear promise: plan, schedule and verify posts across Facebook and Instagram from one workspace. Differentiate with per-platform delivery status, multi-account workflows, and practical recommendations from past posts. Benchmark against the workflows operators already use, including Meta Business Suite and Buffer. [Buffer Facebook scheduler](https://buffer.com/facebook)
- Run publishing reliability and technical SEO in parallel. Prototype onboarding using seeded demo data while publishing status contracts are being finalized. Release the guided workflow after staging verification. Increase acquisition after the canary proves delivery and the funnel can measure first publish and paid conversion.
- Keep the owner as release decision-maker. The AI team will produce small, reviewable changes, test evidence and rollback notes. Publishing to real Meta assets, changing live checkout offers or sending external outreach needs the corresponding owner authorization.

### First implementation batch

- Publishing now uses separate `publish` and `insights` workers, durable claim generations and leases, and per-destination delivery states. The scheduler supports idempotent submissions and edits, reschedules and cancellation before final delivery. A lost final-write response enters verification without being sent again. Legacy ambiguous deliveries migrate into review. Start a rollout with claims paused, then opt approved operators in with `PUBLISH_CANARY_USER_IDS`.
- Reconnects distinguish partial inventory from confirmed revocations. Token generations protect new credentials from older errors and background writes. Manual and background Insights share the same refresh lease, and the nightly worker skips inactive profiles.
- The public site now has server-rendered pricing, page metadata and structured data, a canonical sitemap and robots policy. The host proxy renderer supports apex redirects and protected staging. Review provider callbacks, TLS and Search Console during rollout.
- Remaining rollout evidence includes real Meta format checks on approved assets, Redis/Compose staging and the per-platform canary thresholds. Orphaned-media retention and production latency baselines remain open. The first batch covers the reliability and technical SEO foundation. The activation redesign, broader content pages, retention and pricing experiments remain separate phases.

## P0. Reliable Facebook and Instagram publishing

Exit requirement: an operator can schedule an eligible post and track each destination through delivery, a recoverable delay, or a clear failure. Backend recovery must preserve any provider write that may already have happened.

### P0.1 Dispatch and worker isolation

- [ ] Make `GET /api/posts/scheduled/` read-only. Keep beat or a dedicated recovery task responsible for dispatch and stale work. Use named `publish` and `insights` queues with separately sized workers. During migration, explicitly drain legacy pending deliveries and route each task to one destination. Files: `publishing/views.py`, `publishing/tasks.py`, `social_automation/settings.py`, `deploy/prod/docker-compose.prod.yml`.
- [ ] Select eligible FB work and IG work before applying batch limits. Preserve FIFO within a destination and fair scheduling across accounts, with IG cooldown and per-account serialization. Regression: if the oldest 150 jobs are blocked IG work, a due FB job outside that window still dispatches. Verify a saturated Insights worker does not block publishing.
- [ ] Store the requested publish instant in UTC and retain the display timezone. Use `next_attempt_at` for retries and backoff. For an intentional reschedule, update the requested instant with an audit record. Additive migrations should backfill from the current `scheduled_for` and preserve any existing provider IDs. Identify legacy `processing` rows without IDs before re-enabling recovery. Use a durable DB claim with generation and lease expiry so duplicate Celery messages, overlapping beats and a lost enqueue cannot authorize two final writes. Files: `publishing/models.py`, `publishing/tasks.py`, `publishing/migrations/`.

### P0.2 Per-destination delivery, duplicate prevention and recovery

- [ ] Use a composer-generated idempotency key scoped to the user and canonical request fingerprint. Same key and same payload returns the existing schedule and child jobs. Changed payload with the same key returns a conflict. Each selected platform/account has a stable job identity so partial bulk retries keep accepted jobs intact. Include key reuse after client timeouts in the test. Files: `publishing/views.py`, `publishing/models.py`, `static/dashboard/app.js`.
- [ ] Persist claim generation, attempts, last stage, blocked reason, IG container ID, provider post/media ID, and timestamps. Expose `pending`, `processing`, `retry_wait`, `blocked`, `outcome_unknown`, `published`, `failed`, and `cancelled` consistently in API and UI. For dual posts, show both legs and their individual outcomes. A successful schedule returns queued state. A confirmed provider result records `published`.
- [ ] Mark the final-write boundary before sending a publish request. If the response is lost or the worker dies after that boundary, reconcile from authoritative provider evidence linked to the attempt. Do not automatically resend an ambiguous final write. Time out unresolved cases into an operator review queue and preserve evidence through retry. Permit edit, reschedule and cancel only via a conditional update while the job has not entered final write. Tests: duplicate delivery, crash before and after final write, lost response after Meta accepted it, partial FB+IG success, and cancel racing with claim. Files: `core/services/meta_client.py`, `publishing/services.py`, `publishing/tasks.py`, `publishing/urls.py`.

### P0.3 Account, quota and media safeguards

- [ ] Recheck user entitlement, active account and current token generation at claim and before final write. During reconnect distinguish complete grant inventory, partial/failed lookup and confirmed revocation. Keep account checks scoped by owner and token version. Surface missing permissions and incomplete token resync. Retry temporarily deferred resync jobs with bounded backoff. Verify revoked accounts cannot receive new writes and reconnect does not replay a confirmed leg. Files: `integrations/views.py`, `integrations/services.py`, `integrations/tasks.py`, `publishing/tasks.py`.
- [ ] Defer on known exhausted IG quota before container creation. Use separately classified temporary probe failures and provider cooldown responses. Persist retry time instead of losing the original schedule. Make daily Insights exclude inactive accounts and share the account refresh lock with manual refresh. Regression: `190` deactivation stops the next nightly pull, without deactivating a newly rotated token because an older request returned late. Files: `publishing/services.py`, `analytics/tasks.py`, `analytics/views.py`.
- [ ] Validate platform-specific media before scheduling. Show supported input types and sizes, preview crop and destination, keep the FB original and the IG derivative, and verify Meta can fetch HTTPS media throughout the retry window. Track upload/preflight/preparation errors separately. Remove orphaned media by retention policy after confirming no pending or unresolved job still uses it. Recheck Meta specs against the app's actual Graph version and granted permissions. [Facebook Page Feed](https://developers.facebook.com/docs/graph-api/reference/page/feed/) · [Meta Instagram API collection](https://www.postman.com/meta/instagram/documentation/6yqw8pt/instagram-api?entity=request-23987686-b9dac9f7-5415-4659-bcfd-795298a07e91)
